# ADR-112: Each platform application owns its PostgreSQL cluster

**Date:** 2026-11-02
**Status:** Proposed
**Amends:** ADR-023 (addendum 2026-08-22, the Day-0 bootstrap role), ADR-078 (addendum 5 §6,
Grafana's database), ADR-111 (§2 Class B), ADR-014 (the backup contract, through ADR-014
addendum 3)
**Relates to:** ADR-014 (platform-owned stateful infrastructure), ADR-039 (ownership model),
ADR-076 (reaching a box you own), ADR-092 (recovery is exceptional), ADR-109 (the credit
authority)

## Context

Every PostgreSQL database the hub's platform applications use lives in one CloudNativePG
cluster, `platform-db` (`manifests/hub-core-services/database/`):

| Database | Owner role | Declared by | Consumer |
|---|---|---|---|
| `zitadel` | `hub_zitadel` | `Database` CR | the identity provider |
| `infisical` | `infisical` | `Database` CR + `spec.managed.roles` (ADR-023, Day-0) | the secret store |
| `credits` | `hub_credits` | `Database` CR | the credit authority (ADR-109) |
| `grafana` | `hub_grafana` | `Database` CR | Grafana (ADR-078 addendum 5 §6) |
| `control_plane` | `postgres` | `Database` CR | **none found** — credentials are generated by hub-operator; no workload in the repository connects |
| `hub` | `postgres` | `Database` CR | **none found** — as above |

The cluster has one instance, one 2 GiB memory reservation, one parameter set, one
PostgreSQL image, one extension set, one archive (`spec.backup.barmanObjectStore`, the
in-tree integration) and one daily `ScheduledBackup`. Separation between the applications
is therefore logical only. Each of the following is decided once for all six:

* PostgreSQL version and the timing of its upgrade;
* server parameters, preloaded libraries and available extensions;
* CPU, memory, storage and replica topology;
* backup schedule, retention and recovery point;
* maintenance, failover and restoration.

So a restore is all six or nothing, a parameter tuned for one application is tuned for all
of them, and the identity provider, the secret store and the ledger share one failure domain
with Grafana's sessions.

One dependency is circular. The archive credential, `s3-credentials`, is delivered by ESO
from Infisical. Restoring the cluster that holds Infisical's database therefore needs a key
held by Infisical, which is the one service a hub disaster has taken away. ADR-023's
addendum solved the same loop for the `infisical` role at bootstrap; it was never solved for
recovery.

## Decision

### 1. One cluster per independently managed platform application

Each platform application that owns PostgreSQL state owns a CloudNativePG `Cluster` of its
own. One shared CloudNativePG operator manages all of them; no application installs an
operator.

| Application | Cluster | Database |
|---|---|---|
| Identity provider | `zitadel-db` | `zitadel` |
| Secret store | `infisical-db` | `infisical` |
| Credit authority | `credits-db` | `credits` |
| Grafana | `grafana-db` | `grafana` |

The unit is the application, not the schema: an application with several databases keeps
them in its one cluster.

**`control_plane` and `hub` get no cluster.** Nothing in the platform connects to either. A
cluster is provisioned for a database when a consumer is identified; a database with no
consumer is removed rather than carried into the new layout, and its removal is recorded in
the transition plan with the evidence that nothing reads it.

### 2. What each cluster owns

Every cluster carries its whole lifecycle, and nothing about it is inherited from another
application's cluster:

* its `Cluster` resource, `Database` resource and owner role;
* its PostgreSQL image and extensions, declared through CloudNativePG's native mechanisms
  (image selection and the `Database` resource's declared extensions) at a version the
  deployed operator supports. Extensions are never installed into a running container, and
  no extension controller is added;
* its parameters, CPU, memory and storage, sized from that application's measured use. The
  shared cluster's 2 GiB is not copied;
* its credentials and role reconciliation, and its own read-write service endpoint;
* a `Pooler` only where the application needs one;
* a NetworkPolicy admitting its application and the operator, and nothing else;
* its own object store, archive identity, backup schedule and retention (ADR-014 addendum 3);
* its recovery configuration and runbook, under ADR-092.

### 3. Replicas and placement

The replica ladder is the platform's: one instance in development, two in staging, three in
production (as ADR-078 addendum 7 applies it to the observability stores). Stateful
placement follows ADR-014's rule: worker nodes only, never tolerating the control-plane
taint.

A replica count is not a claim of availability. A cluster is described as highly available
only once its instances are shown to sit on separate nodes, on storage that survives the loss
of one, with failover exercised. Development must stay schedulable within the hub's capacity,
so the transition plan states the total requested by all clusters before the first one is
created.

### 4. Infisical's cluster recovers without Infisical

Everything needed to restore `infisical-db` — the read credential for its archive and the
keys its data is encrypted with — is available before Infisical runs: the archive credential
from the escrow (ADR-076, ADR-111 Class E), the master keys as ADR-111 §1 already scopes
them. No other cluster may become a dependency of Infisical's recovery. The other clusters'
archive credentials may continue to arrive from Infisical, because Infisical is restored
before them (ADR-111, Revision 5).

### 5. Transition

The current state is preserved throughout. The transition is a logical separation of
databases, not six physical copies of `platform-db`:

* Each application moves on its own, using CloudNativePG's database import
  (`bootstrap.initdb.import`, microservice type), where the source and destination PostgreSQL
  versions are compatible.
* Before data moves, the destination's backup and restore are proven (ADR-111, Revision 5).
* Writes are quiesced for the cutover. The source and the destination never both accept
  writes, during or after.
* Data, extensions, ownership, privileges and schema version are verified on the destination
  before the application's connection is moved, declaratively, to it.
* The source database is kept for rollback until the destination is verified in use and
  backed up. A healthy `Cluster` status is not that verification.
* Grafana moves first, as the lowest-risk proof of the whole procedure. The secret store, the
  identity provider and the ledger are critical-state moves, each with integrity checks before
  and after.
* No hidden dependency on `platform-db` survives: bootstrap SQL, `managed.roles`,
  hub-operator's RoleManager, the password-rotation job, migration jobs, connection Secrets,
  service names and network policies are each moved or removed.

None of this starts until ADR-111 Revision 5's recovery work has proven the current archive
restorable. `platform-db` is retired only after the last application has moved and been
verified.

## Ownership

| Resource Class | System of Record | Lifecycle Owner | Reconciler | Consumer | Phase |
|---|---|---|---|---|---|
| An application's PostgreSQL cluster | PostgreSQL | Platform | CloudNativePG | that application | Day-1+ |
| `infisical-db`, its role and database | PostgreSQL | Platform | CloudNativePG | Infisical | Day-0 (ADR-023) |
| An application's database contents | PostgreSQL | the application | the application's migrations | the application | Day-1+ |
| An application's archive and base backups | object storage | Platform | CloudNativePG (Barman Cloud plugin) | recovery (ADR-111) | Day-1+ |
| `infisical-db`'s archive read credential | escrow (ADR-076) | Platform | — | recovery | Day-0 |

## Consequences

### Positive

1. Each application chooses its PostgreSQL version, extensions, parameters, size and upgrade
   timing without negotiating with the others.
2. A restore, a failover or a bad parameter affects one application.
3. Backup schedules and recovery points follow each application's value: the ledger's need not
   be Grafana's.
4. Infisical's recovery no longer depends on Infisical.

### Negative

1. Four clusters instead of one: more pods, more memory and more storage on the hub, and four
   archives and schedules to watch.
2. Recovery points are independent per application, so a restore of several is not a
   consistent snapshot of the platform (ADR-111, Revision 5).
3. Four migrations, each with a write quiesce, before `platform-db` can be retired.
4. No query can join across applications' databases. None is known to; the inventory step of
   each move confirms it.

## Impact

* `manifests/hub-core-services/database/`: one cluster definition per application, each with
  its database, role, credentials, network policy, object store and backup schedule;
  `platform-db` retired at the end.
* hub-operator's RoleManager and generated database credentials: each role targets its
  application's cluster; the `control_plane` and `hub` credentials go with their databases.
* Each application's connection settings move to its cluster's endpoint.
* The escrow gains `infisical-db`'s archive read credential.
* ADR-023, ADR-078, ADR-111 and ADR-014 are amended as listed at the top.
* Migration procedures and cutover order live in `docs/plans/adr-112-database-isolation.md`.
